Katana purchase order automation: Google Sheets → Make → Katana

We tested a controlled purchasing workflow with exact supplier/SKU validation, duplicate protection, success writeback and fail-closed handling before any unsafe Katana write.

Hands-on evidenceProduction acceptance passedScope: purchasing automation only
Bottom line. The hardened workflow passed the failure-path retest and the valid recovery test. An invalid SKU was blocked before a Katana PO was created; a valid request in the same controlled run completed and created Katana PO 2945674.

What we tested

The lab used a Google Sheets queue as the controlled request layer, Make as the orchestration layer and Katana as the purchasing system. The purpose was not to prove every Katana feature. It was to answer a narrower operational question: can a small manufacturer automate purchase-order creation without silently creating bad purchasing data when supplier, SKU or idempotency checks fail?

The failure-path result mattered more than the happy path

An earlier test exposed a dangerous pattern: an invalid SKU could continue through the lookup chain and later fail on a missing variant ID. The hardened workflow changed the gate placement so validation uses the output of the preceding lookup rather than a self-referential filter. In the retest, the deliberately invalid SKU RM-NOT-EXIST ended BLOCKED_VALIDATION, recorded the validation error, and produced no Katana PO ID.

T03R result: fail closed. Supplier: Bright Components Ltd. SKU: RM-NOT-EXIST. Queue status: BLOCKED_VALIDATION. Katana PO ID: none.

Recovery-path result

Fail-closed logic is only useful if it does not block valid purchasing. A valid request for CleanChem Supplies / PKG-CLEAN-BTL was processed in the same controlled execution window and created Katana PO 2945674.

T04 result: valid recovery path. Queue status: PROCESSED. Katana PO ID: 2945674.

What this evidence does — and does not — prove

This test gives us first-hand evidence about controlled PO automation, validation, idempotency and writeback. It does not yet prove Shopify order/stock synchronization, QuickBooks mapping, the full multi-level production workflow, outsourced production, broad export completeness or Katana's overall fit for every manufacturer. Those remain separate test claims.

That distinction is intentional. MFG Stack Lab publishes narrow tested conclusions before it publishes a full product score.

Where this workflow fits

  • Teams still using spreadsheets as a purchasing intake layer.
  • Manufacturers that want human-readable queues but automated Katana writes.
  • Businesses where bad SKU/supplier mappings are more costly than a blocked request.
  • Operators who require idempotency and visible failure states before unattended automation.

Next decision
